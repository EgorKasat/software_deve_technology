## 1. Введение

### Что такое принципы разработки ПО?

**Принципы разработки ПО** — это набор проверенных правил и рекомендаций,
которые помогают создавать код, который легко:

- читать 👀
- поддерживать 🔧
- тестировать 🧪
- расширять ➕
- переиспользовать ♻️

### Зачем они нужны?

Программное обеспечение живёт годами и десятилетиями. За это время:

- **меняются требования** — бизнес хочет новые фичи;
- **меняются разработчики** — команда растёт и сменяется;
- **меняются технологии** — библиотеки устаревают;
- **растёт сложность** — кодовая база увеличивается.

Принципы помогают **снизить стоимость изменений** и **уменьшить количество
багов**. Они — не догма, а ориентиры, которые работают в большинстве
ситуаций, но требуют здравого смысла.

### Ключевая метрика

> Хороший код — это код, который **легко изменить**.

Не «короткий», не «умный», не «оптимальный» — а именно **изменяемый**.

## 2. KISS — Keep It Simple, Stupid

> «Не усложняй там, где можно сделать проще.»

### Суть

Самое простое решение, которое работает, — обычно лучшее. Сложность — враг
надёжности, читаемости и поддерживаемости.

### Почему это важно?

- Простой код **легче понять** новому разработчику.
- Простой код **меньше багует** — меньше мест, где что-то может пойти не так.
- Простой код **быстрее работает** (обычно).
- Простой код **дешевле поддерживать**.

### Примеры

❌ **Плохо** — избыточная логика:
```python
def is_even(n):
    if n % 2 == 0:
        return True
    else:
        return False
```

✅ **Хорошо** — одна строка:
```python
def is_even(n):
    return n % 2 == 0
```

❌ **Плохо** — переусложнённая архитектура для маленькой задачи:
```python
# Для парсинга CSV-файла создаётся фабрика, стратегия и наблюдатель
parser = CSVParserFactory.create(
    CSVParserStrategy(Observer(CSVVisitor()))
)
```

✅ **Хорошо** — просто и понятно:
```python
import csv

with open("data.csv") as f:
    rows = list(csv.reader(f))
```

### Когда KISS можно нарушить?

- Когда простое решение объективно **не справляется** с нагрузкой.
- Когда сложность **оправдана требованиями** (например, безопасность,
  производительность).
- Когда вы **точно знаете**, что простого решения хватит надолго.

### Антипаттерн: преждевременная оптимизация

> «Преждевременная оптимизация — корень всех зол.» — Дональд Кнут

Не оптимизируй то, что ещё не работает. Сначала — простое рабочее решение,
потом — измерения, потом — оптимизация **узких мест**.

## 3. DRY — Don't Repeat Yourself

> «Каждая единица знания должна иметь единственное представление в системе.»

### Суть

Дублирование логики → дублирование багов и правок. Если правило меняется,
менять его нужно в одном месте, а не в десяти.

### Примеры

❌ **Плохо** — дублирование формулы:
```python
area1 = 3.14 * r1 * r1
area2 = 3.14 * r2 * r2
area3 = 3.14 * r3 * r3
```

✅ **Хорошо** — одна функция:
```python
import math

def circle_area(r):
    return math.pi * r ** 2

area1 = circle_area(r1)
area2 = circle_area(r2)
area3 = circle_area(r3)
```

❌ **Плохо** — дублирование валидации:
```python
def register_user(email):
    if "@" not in email:
        raise ValueError("Invalid email")
    ...

def send_email(email):
    if "@" not in email:
        raise ValueError("Invalid email")
    ...
```

✅ **Хорошо** — вынесенная валидация:
```python
def validate_email(email):
    if "@" not in email:
        raise ValueError("Invalid email")

def register_user(email):
    validate_email(email)
    ...

def send_email(email):
    validate_email(email)
    ...
```

### ⚠️ Важно: DRY — про *знания*, а не про код

DRY **не означает**, что любой похожий код нужно объединять. Если два
фрагмента **выглядят одинаково**, но **меняются по разным причинам** —
их объединять **нельзя**.

❌ **Ложное следование DRY**:
```python
# Два разных отчёта с одинаковой структурой — но разной логикой
def generate_report(data, type):
    if type == "sales":
        # логика продаж
    elif type == "users":
        # логика пользователей
```

✅ **Правильно** — оставить раздельно:
```python
def generate_sales_report(data): ...
def generate_users_report(data): ...
```

### Связанные принципы

- **DRY** ↔ **KISS**: объединение похожего кода может усложнить систему.
- **DRY** ↔ **SRP**: одна причина для изменения = одна единица знания.
- **DRY** ↔ **WET** (Write Everything Twice) — антипод.

## 4. YAGNI — You Aren't Gonna Need It

> «Не реализуй то, что не требуется сейчас.»

### Суть

Не пиши функциональность «на будущее» — оно может никогда не наступить,
а поддержка уже стоит времени **сегодня**.

### Признаки нарушения YAGNI

- Абстракции «на случай, если понадобится».
- Параметры функций, которые никто не передаёт.
- Классы, у которых только один наследник «пока что».
- Конфигурируемость всего подряд.

### Примеры

❌ **Плохо** — функция с 10 параметрами «на всякий случай»:
```python
def create_user(name, age, email=None, phone=None,
                address=None, nickname=None, avatar=None,
                locale=None, timezone=None, theme=None):
    ...
```

✅ **Хорошо** — только нужное сейчас:
```python
def create_user(name, age, email):
    ...
```

❌ **Плохо** — абстракция для одного случая:
```python
class AbstractUserFactory:
    def create(self): ...

class ConcreteUserFactory(AbstractUserFactory):
    def create(self): return User()
```

✅ **Хорошо** — просто класс:
```python
class User:
    ...
```

### Как применять?

- **Реализуй минимально работающее решение.**
- **Рефактори, когда появится реальная потребность.**
- **Не строй абстракции до третьего повторения** (правило трёх).

### Правило трёх (Rule of Three)

> Дублируй один раз. При втором повторении — задумайся. При третьем —
> рефактори.

Это балансирует YAGNI и DRY: не абстрагируй раньше времени, но и не
дублируй бесконечно.

## 5. SOLID

Пять принципов ООП-дизайна, сформулированных Робертом Мартином
(акроним введён Майклом Физерсом).

### S — Single Responsibility Principle (SRP)

> У класса должна быть **одна причина для изменения**.

#### Суть

Класс должен отвечать за **одну задачу**. Если класс меняется по нескольким
причинам — это признак нарушения SRP.

#### Пример

❌ **Плохо** — класс делает и расчёт, и сохранение:
```python
class Report:
    def calculate(self): ...
    def format(self): ...
    def save_to_pdf(self): ...
    def send_by_email(self): ...
```

✅ **Хорошо** — разделение ответственности:
```python
class ReportCalculator:
    def calculate(self): ...

class ReportFormatter:
    def format(self, report): ...

class PdfExporter:
    def export(self, report): ...

class EmailSender:
    def send(self, report): ...
```

#### Как определить нарушение?

Задай вопрос: **«Сколько причин может заставить этот класс измениться?»**

- Одна → SRP соблюдён.
- Больше одной → SRP нарушен.

---

### O — Open/Closed Principle (OCP)

> Классы открыты для **расширения**, но закрыты для **изменения**.

#### Суть

Новое поведение добавляется через **расширение** (наследование,
композиция, стратегии), а не через **правку** существующего кода.

#### Пример

❌ **Плохо** — каждый новый тип требует правки функции:
```python
def area(shape):
    if shape.type == "circle":
        return math.pi * shape.r ** 2
    elif shape.type == "square":
        return shape.side ** 2
    elif shape.type == "triangle":   # ← нужно менять функцию
        ...
```

✅ **Хорошо** — полиморфизм:
```python
class Shape:
    def area(self): ...

class Circle(Shape):
    def area(self):
        return math.pi * self.r ** 2

class Square(Shape):
    def area(self):
        return self.side ** 2

# Новый тип добавляется без правки существующего кода
class Triangle(Shape):
    def area(self):
        return 0.5 * self.base * self.height
```

#### Инструменты

- Наследование и полиморфизм.
- Паттерн **Strategy**.
- Паттерн **Decorator**.
- Функции высшего порядка.

---

### L — Liskov Substitution Principle (LSP)

> Подклассы должны **заменять** базовый класс без поломки логики.

#### Суть

Если `S` — подкласс `T`, то объекты `T` можно заменить на `S` **без
нарушения корректности программы**.

#### Классический пример нарушения

```python
class Rectangle:
    def set_width(self, w): self.w = w
    def set_height(self, h): self.h = h
    def area(self): return self.w * self.h

class Square(Rectangle):
    def set_width(self, w):
        self.w = self.h = w   # меняет и высоту!
    def set_height(self, h):
        self.w = self.h = h   # меняет и ширину!
```

```python
def resize(rect: Rectangle):
    rect.set_width(5)
    rect.set_height(4)
    assert rect.area() == 20   # 💥 для Square получится 16
```

#### Как соблюдать?

- Подкласс **не должен усиливать** предусловия.
- Подкласс **не должен ослаблять** постусловия.
- Подкласс **не должен бросать** новые исключения.
- Подкласс **не должен менять** семантику родительских методов.

#### Признаки нарушения

- `isinstance` / `type()` проверки в коде.
- Методы, которые бросают `NotImplementedError`.
- Пустые реализации унаследованных методов.

---

### I — Interface Segregation Principle (ISP)

> Клиент не должен зависеть от методов, которые он не использует.

#### Суть

Лучше много **маленьких** интерфейсов, чем один **большой**.

#### Пример

❌ **Плохо** — «толстый» интерфейс:
```python
class Machine:
    def print(self): ...
    def scan(self): ...
    def fax(self): ...

class OldPrinter(Machine):
    def print(self): ...
    def scan(self):
        raise NotImplementedError   # 💥 не умеет
    def fax(self):
        raise NotImplementedError   # 💥 не умеет
```

✅ **Хорошо** — разделение интерфейсов:
```python
class Printer:
    def print(self): ...

class Scanner:
    def scan(self): ...

class Fax:
    def fax(self): ...

class OldPrinter(Printer):
    def print(self): ...
```

#### Как определить нарушение?

Если класс реализует метод, который **никогда не вызывается** или
**бросает исключение** — интерфейс слишком большой.

---

### D — Dependency Inversion Principle (DIP)

> Зависимости от **абстракций**, а не от конкретных реализаций.

#### Суть

- Модули верхнего уровня **не должны зависеть** от модулей нижнего уровня.
- Оба должны зависеть от **абстракций**.
- Абстракции **не должны зависеть** от деталей.

#### Пример

❌ **Плохо** — жёсткая привязка к MySQL:
```python
class Order:
    def __init__(self):
        self.db = MySQLDatabase()   # 💥 нельзя заменить
```

✅ **Хорошо** — зависимость от абстракции:
```python
class Database(ABC):
    @abstractmethod
    def insert(self, data): ...

class MySQLDatabase(Database):
    def insert(self, data): ...

class PostgresDatabase(Database):
    def insert(self, data): ...

class Order:
    def __init__(self, db: Database):   # ← абстракция
        self.db = db
```

#### Практическая польза

- Легко менять реализации (MySQL → PostgreSQL).
- Легко тестировать (моки вместо реальной БД).
- Слабая связанность модулей.

## 6. Separation of Concerns (SoC)

> Разделяй программу на части, каждая из которых отвечает за **отдельный
> аспект**.

### Суть

Разные аспекты системы (UI, бизнес-логика, доступ к данным) должны быть
**разделены** на отдельные модули/слои.

### Классические примеры

- **MVC** — Model, View, Controller.
- **MVVM** — Model, View, ViewModel.
- **Слоистая архитектура** — UI → Service → Repository → DB.
- **Hexagonal architecture** (Ports & Adapters).
- **Clean Architecture** (Роберт Мартин).

### Схема слоёв

```
┌─────────────────────────────┐
│  UI / Presentation          │  ← что видит пользователь
├─────────────────────────────┤
│  Application / Use Cases    │  ← сценарии использования
├─────────────────────────────┤
│  Domain / Business Logic    │  ← правила бизнеса
├─────────────────────────────┤
│  Infrastructure / Data      │  ← БД, API, файлы
└─────────────────────────────┘
```

### Практическая польза

- Можно менять UI **без переписывания логики**.
- Можно менять БД **без переписывания UI**.
- Легче тестировать каждый слой **изолированно**.
- Легче распределять работу между командами.

## 7. Инкапсуляция

> Скрывай детали реализации, предоставляй **чистый интерфейс**.

### Суть

Внутреннее состояние объекта **скрыто** от внешнего мира. Доступ — только
через **публичные методы**, которые контролируют корректность.

### Пример

```python
class BankAccount:
    def __init__(self):
        self.__balance = 0          # приватное поле

    def deposit(self, amount):      # публичный метод
        if amount <= 0:
            raise ValueError("Сумма должна быть положительной")
        self.__balance += amount

    def withdraw(self, amount):
        if amount > self.__balance:
            raise ValueError("Недостаточно средств")
        self.__balance -= amount

    @property
    def balance(self):
        return self.__balance       # только чтение
```

### Преимущества

- **Контроль инвариантов** — состояние всегда корректно.
- **Свобода изменений** — внутреннюю реализацию можно переписать.
- **Уменьшение связанности** — клиенты не зависят от деталей.

### Уровни доступа

| Язык      | Приватность                                         |
|-----------|-----------------------------------------------------|
| Python    | `_protected`, `__private` (name mangling)           |
| Java      | `private`, `protected`, `public`, `package-private` |
| C++       | `private`, `protected`, `public`                    |
| TypeScript| `private`, `protected`, `public`, `readonly`        |

## 8. Слабая связанность и высокая связность

### Определения

| Характеристика       | Значение                                      |
|----------------------|-----------------------------------------------|
| **Low coupling**     | Модули мало зависят друг от друга             |
| **High cohesion**    | Внутри модуля — только логически близкое      |

✅ Цель: **минимум зависимостей между модулями**, **максимум связности
внутри**.

### Примеры

❌ **Сильная связанность** — жёсткая привязка к БД:
```python
class OrderService:
    def create(self):
        db = MySQLDatabase("localhost", "root", "1234")
        db.insert(...)
```

✅ **Слабая связанность** — зависимость передаётся извне:
```python
class OrderService:
    def __init__(self, db):     # DI
        self.db = db

    def create(self, order):
        self.db.insert(order)
```

❌ **Низкая связность** — модуль делает всё подряд:
```python
class Utils:
    def send_email(self): ...
    def calculate_tax(self): ...
    def resize_image(self): ...
    def parse_date(self): ...
```

✅ **Высокая связность** — модуль делает одну вещь:
```python
class EmailSender:
    def send(self, to, subject, body): ...

class TaxCalculator:
    def calculate(self, amount): ...

class ImageResizer:
    def resize(self, image, size): ...
```

### Как измерить?

- **Coupling** — количество зависимостей модуля от других.
- **Cohesion** — насколько методы класса связаны друг с другом.
- **LCOM** (Lack of Cohesion in Methods) — метрика.

## 9. Композиция над наследованием

> Предпочитай **включать** поведение, а не **наследовать** его.

### Суть

Наследование создаёт **жёсткую связь** между классами. Композиция —
**гибкую**.

### Проблема наследования

❌ **Взрыв иерархии**:
```python
class Animal: ...
class FlyingAnimal(Animal): ...
class SwimmingAnimal(Animal): ...
class FlyingSwimmingAnimal(FlyingAnimal, SwimmingAnimal): ...  # 💥
class FlyingSwimmingWalkingAnimal(...): ...                    # 💥💥
```

### Решение — композиция

✅ **Гибко и расширяемо**:
```python
class FlyBehavior:
    def fly(self): ...

class SwimBehavior:
    def swim(self): ...

class WalkBehavior:
    def walk(self): ...

class Duck:
    def __init__(self):
        self.fly_behavior = FlyWithWings()
        self.swim_behavior = SwimInWater()
        self.walk_behavior = WalkOnLand()
```

### Паттерн Strategy

```python
class PaymentStrategy(ABC):
    @abstractmethod
    def pay(self, amount): ...

class CardPayment(PaymentStrategy):
    def pay(self, amount): ...

class CryptoPayment(PaymentStrategy):
    def pay(self, amount): ...

class Order:
    def __init__(self, payment: PaymentStrategy):
        self.payment = payment

    def checkout(self, amount):
        self.payment.pay(amount)
```

### Когда наследование уместно?

- Отношение **«является»** (is-a), а не **«имеет»** (has-a).
- **Неглубокая** иерархия (1–2 уровня).
- Базовая логика **не меняется** в подклассах.
- Нет **ромбовидного** наследования.

## 10. Принцип наименьшего удивления (POLA)

> Код должен вести себя **предсказуемо** для читателя.

### Суть

Название функции, метода или класса должно **соответствовать** тому, что
оно делает. Никаких «сюрпризов».

### Примеры нарушений

❌ **Функция удаляет, хотя называется get**:
```python
def get_user(user_id):
    db.delete(user_id)   # 🤯 почему удаляет?
    return None
```

✅ **Ожидаемое поведение**:
```python
def get_user(user_id):
    return db.find(user_id)

def delete_user(user_id):
    db.delete(user_id)
```

❌ **Флаг меняет формат вывода**:
```python
def format_date(date, verbose=False):
    if verbose:
        return date.strftime("%Y-%m-%d %H:%M:%S")  # 🤯 совсем другой формат
```

✅ **Флаг добавляет детали, а не меняет формат**:
```python
def format_date(date, with_time=False):
    fmt = "%Y-%m-%d %H:%M" if with_time else "%Y-%m-%d"
    return date.strftime(fmt)
```

### Классический пример из Python

- `list.sort()` — сортирует **на месте**, возвращает `None`.
- `sorted(list)` — возвращает **новый** список.

Это ожидаемое поведение, и оно **согласовано** внутри языка.

### Практические правила

- Имя функции = действие, которое она выполняет.
- Параметры не должны **неожиданно** менять поведение.
- Побочные эффекты должны быть **очевидны**.
- Исключения бросаются только в **исключительных** случаях.

## 11. Fail Fast

> Ошибку лучше обнаружить **как можно раньше**.

### Суть

Программа должна **немедленно** сообщать об ошибке, а не продолжать работу
в некорректном состоянии.

### Примеры

✅ **Проверка на входе**:
```python
def divide(a, b):
    if b == 0:
        raise ValueError("Деление на ноль")
    return a / b
```

✅ **Валидация конфигурации при старте**:
```python
def load_config(path):
    with open(path) as f:
        config = json.load(f)

    required = ["database_url", "api_key"]
    for key in required:
        if key not in config:
            raise ConfigError(f"Отсутствует обязательный ключ: {key}")

    return config
```

✅ **Assert в тестах и инвариантах**:
```python
def transfer(from_acc, to_acc, amount):
    assert amount > 0, "Сумма должна быть положительной"
    assert from_acc.balance >= amount, "Недостаточно средств"
    ...
```

### Плюсы

- **Понятные стектрейсы** — ошибка видна сразу.
- **Меньше «тихих» багов** — некорректное состояние не распространяется.
- **Проще отладка** — ошибка ближе к источнику.
- **Безопаснее** — программа не работает с некорректными данными.

### Антипаттерн: Silent Failure

❌ **Плохо** — ошибка «проглатывается»:
```python
def parse_int(s):
    try:
        return int(s)
    except ValueError:
        return 0   # 🤯 молча вернули 0
```

✅ **Хорошо** — ошибка явно сообщается:
```python
def parse_int(s):
    try:
        return int(s)
    except ValueError as e:
        raise ValueError(f"Не удалось распарсить '{s}'") from e
```

## 12. Тестируемость

> Хороший код легко покрывается тестами.

### Принципы тестируемого кода

- **Маленькие функции** с одной задачей.
- **Зависимости через параметры** (Dependency Injection).
- **Отсутствие глобального состояния**.
- **Детерминированность** — одинаковый вход → одинаковый выход.
- **Изоляция** от внешних систем (БД, API, файлы).

### Пирамида тестов

```
       ┌─────────────┐
       │     E2E     │  ← мало, медленные, дорогие
       ├─────────────┤
       │ Integration │  ← среднее количество
       ├─────────────┤
       │    Unit     │  ← много, быстрые, дешёвые
       └─────────────┘
```

### Пример unit-теста

```python
def test_circle_area():
    assert circle_area(2) == pytest.approx(12.566, rel=1e-3)

def test_circle_area_zero():
    assert circle_area(0) == 0

def test_circle_area_negative():
    with pytest.raises(ValueError):
        circle_area(-1)
```

### Пример с моком

```python
def test_order_creation():
    mock_db = Mock()
    service = OrderService(db=mock_db)

    service.create(Order(id=1))

    mock_db.insert.assert_called_once()
```

### Что делает код тестируемым?

| Признак                     | Почему важно                          |
|-----------------------------|---------------------------------------|
| DI                          | Легко подменить зависимость           |
| Чистые функции              | Нет побочных эффектов                 |
| Маленькие классы            | Легко изолировать                     |
| Отсутствие синглтонов       | Нет скрытого состояния                |
| Явные интерфейсы            | Легко мокать                          |

### Anti-patterns

- Тесты, зависящие от **порядка выполнения**.
- Тесты, работающие с **реальной БД** без изоляции.
- Тесты с **`sleep()`**.
- Тесты, которые **иногда падают** (flaky tests).

## 13. Читаемость кода

> «Код читают в 10 раз чаще, чем пишут.» — Мартин Фаулер

### Правила

#### 1. Осмысленные имена

❌ **Плохо**:
```python
x = 10
y = x * 2
```

✅ **Хорошо**:
```python
base_price = 10
total_price = base_price * 2
```

#### 2. Короткие функции

Функция должна помещаться **на один экран** (~20–30 строк).

#### 3. Комментарии — про **почему**, а не **что**

❌ **Плохо**:
```python
# Увеличиваем i на 1
i += 1
```

✅ **Хорошо**:
```python
# Пропускаем заголовок CSV-файла
i += 1
```

#### 4. Единый стиль

- Python — **PEP 8**.
- JavaScript — **ESLint + Prettier**.
- Go — **gofmt**.
- Java — **Google Java Style**.

#### 5. Избегай «магических чисел»

❌ **Плохо**:
```python
if u.s >= 18 and u.s <= 65:
    ...
```

✅ **Хорошо**:
```python
WORKING_AGE_MIN = 18
WORKING_AGE_MAX = 65

if WORKING_AGE_MIN <= user.age <= WORKING_AGE_MAX:
    ...
```

#### 6. Не комментируй плохой код — перепиши его

❌ **Плохо**:
```python
# Эта функция проверяет, что пользователь активен
# и у него есть права на редактирование
def check(u):
    return u.a and u.p > 2
```

✅ **Хорошо**:
```python
def can_edit(user):
    return user.is_active and user.permission_level > 2
```

### Принципы именования

| Тип            | Стиль            | Пример                |
|----------------|------------------|-----------------------|
| Переменная     | snake_case       | `user_count`          |
| Константа      | UPPER_SNAKE      | `MAX_RETRIES`         |
| Функция        | snake_case       | `get_user_by_id`      |
| Класс          | PascalCase       | `UserRepository`      |
| Приватное      | `_prefix`        | `_internal_state`     |
| Модуль         | snake_case       | `user_service.py`     |

## 14. Антипаттерны

Принципы полезно знать вместе с их **антиподами** — типичными ошибками.

### 1. God Object

Класс, который «знает всё и умеет всё».

```python
class Application:
    def handle_request(self): ...
    def connect_to_db(self): ...
    def render_html(self): ...
    def send_email(self): ...
    def calculate_tax(self): ...
    def log(self): ...
    # ...ещё 100 методов
```

**Лечение:** разделить на несколько классов по SRP.

### 2. Spaghetti Code

Код без структуры, с запутанными переходами и связями.

**Лечение:** рефакторинг, выделение функций и модулей.

### 3. Copy-Paste Programming

Копирование кода вместо его переиспользования.

**Лечение:** DRY, выделение общих функций.

### 4. Premature Optimization

Оптимизация до того, как стало ясно, что это узкое место.

**Лечение:** KISS, измерения, профилирование.

### 5. Magic Numbers / Strings

Числа и строки без объяснения.

**Лечение:** именованные константы.

### 6. Shotgun Surgery

Одно изменение требует правок в десятке мест.

**Лечение:** SRP, DRY, инкапсуляция.

### 7. Feature Envy

Метод класса A слишком часто обращается к данным класса B.

**Лечение:** перенести метод в класс B.

### 8. Circular Dependencies

Модуль A зависит от B, B — от A.

**Лечение:** выделить общий интерфейс/модуль, DIP.

## 15. Итоговая шпаргалка

| Принцип                | Кратко                                          |
|------------------------|-------------------------------------------------|
| **KISS**               | Делай проще                                     |
| **DRY**                | Не дублируй знания                              |
| **YAGNI**              | Не делай «на будущее»                           |
| **SRP**                | Один класс — одна ответственность               |
| **OCP**                | Открыт для расширения, закрыт для изменения     |
| **LSP**                | Подкласс заменяет родителя без сюрпризов        |
| **ISP**                | Много маленьких интерфейсов > один большой      |
| **DIP**                | Зависи от абстракций, не от реализаций          |
| **SoC**                | Разделяй ответственности по слоям               |
| **Инкапсуляция**       | Скрывай детали реализации                       |
| **Low coupling**       | Слабая связанность модулей                      |
| **High cohesion**      | Высокая связность внутри модуля                 |
| **Композиция > насл.** | Включай поведение, а не наследуй                |
| **POLA**               | Код должен удивлять как можно меньше            |
| **Fail Fast**          | Падай рано и громко                             |
| **Тестируемость**      | Код должен легко покрываться тестами            |
| **Читаемость**         | Код — для людей, не для машин                   |

## 🎯 Вывод

Принципы разработки ПО — это **инструменты**, а не правила ради правил.
Их задача — сделать систему:

- **простой** (KISS, YAGNI),
- **гибкой** (SOLID, OCP, DIP),
- **поддерживаемой** (DRY, SoC, читаемость),
- **надёжной** (Fail Fast, тесты).

> Хороший код — это код, который **легко изменить**.

### Как применять принципы на практике?

1. **Пиши просто** — не усложняй без необходимости.
2. **Не дублируй** — но и не абстрагируй раньше времени.
3. **Разделяй ответственности** — SRP, SoC.
4. **Зависи от абстракций** — DIP, слабая связанность.
5. **Пиши тесты** — они улучшают дизайн.
6. **Рефактори регулярно** — код не «застывает».
7. **Читай чужой код** — учись на хороших примерах.

### Баланс принципов

Принципы **иногда конфликтуют** друг с другом:

- **DRY** ↔ **KISS** — объединение похожего кода может усложнить систему.
- **YAGNI** ↔ **OCP** — абстракции «на будущее» противоречат YAGNI.
- **SRP** ↔ **ISP** — много маленьких классов vs много маленьких интерфейсов.

**Главное правило:** применяй принципы **осознанно**, а не механически.
Их цель — **упростить жизнь**, а не усложнить.
